# LEF Layout Editor MVP

## Overview

This is a Minimum Viable Product (MVP) and proof of concept to develop a full-stack solution for editing Electronic Design Automation (EDA) Computer Aided Design (CAD) data in LEF/DEF and SystemVerilog formats.

The purpose of this project is to determine the best software architecture to use for editing complex, hierarchical designs with millions of objects.

We will start by implementing a simple LEF editor, which can read multiple LEF files and provide a C API which is used in a Flutter plugin to display a Texture.

The backend project is used to process a database, into a set of skia commands which will create an SkPicture that can be sent to Flutter via a pixel buffer.

The process will be developed using a multi-threaded, layer based, render pipeline.

## Requirements

- Target platform is linux servers, with little or no GPU support.
- Must be as memory and CPU efficient as possible.
- Tests must be developed in parallel with code.
- Code must be structure in a clean, reusable way, with appropriate use of abstraction.
- Target C++ language is c++23.
- All code must be benchmarked so decisions are data driven.
- Code must be concise and well documented.

- All interactions should be concise and not overly verbose.

## Existing code

- **database** - contains a database structure that uses an object pool and IDs to store data read from a LEF file. The code is generated by a Python utility based on the data in schema.py.
- **io** - contains a LEF parser which reads LEF files into the database structure.

## Features

- The pipeline should have the following stages (order to be determined by benchmarking):
  - Shape generation - reads an Abstract from the database to generate shapes for all the objects, in database units (dbu).
  - Shape filter - removes shapes that are outside the users "viewport" and small shapes that are less than 1 pixel wide. The sub-pixel test is done in dbu-space (comparing against `1px / scale`) rather than transforming every shape first, so nothing is transformed until after culling.
  - Layer filter - layer visibility can be toggled.
  - The dbu → pixel transform (scale + pan + viewport offset) is not a separate stage: it's the last step of rendering, applied only to shapes that survive filtering.

- Events
  - Events are triggered from Flutter via the C API, including:
    - Reading LEF files
    - Clicking on toolbar buttons
  - Events are also triggered from inside the surface, including:
    - Mouse movement
    - Object selection
    - Object resize and movement

- Property editing
  - When objects are selected, a property editor, in flutter, can be used to edit the properties of database objects.

### Module breakdown (dependency order)

- **`database`** *(exists)* — schema-driven object-pool database (`Root`, generational `XxxId` handles, per-class pools). Source of truth for all layout/schematic data; every other module depends on this.
- **`geometry`** *(exists)* — bbox, overlap/hit-test, transform, polygon union/buffer, and label-placement operations over `le::Point/Rect/Polygon/Path`, backed by Boost.Geometry (ported from the sibling project's `utils/geometry.hpp`, the one part of it that was real and working). Turned out to be a hard compile-time dependency of `io` (LEF macro boundary/obstruction generation calls `Geometry::union_shapes`/`rect_to_polygon`/`transform` directly), not just a pipeline-filter nicety — built in full rather than as a stub. Depends on: `database`.
- **`io`** *(exists)* — format readers that populate `Root` from external files. Currently `LEFReader`, compiling and passing tests against the vendored `src/lefdef/lef` parser; DEF and SystemVerilog netlist readers land here later. Depends on: `database`, `geometry`.
- **`view_style`** *(exists)* — `ViewLayerSet`/`ViewLayer`: the rendering-purpose layer concept (`TERMINAL`/`OBSTRUCTION` per physical LEF `Layer`, plus one `BOUNDARY` layer with no physical `Layer`), kept separate from the LEF-mirroring `database` since it's purely a rendering/application concept, not LEF vocabulary. Also owns `ViewLayerStyle` (outline/fill color) per `ViewLayer`. Depends on: `database`.
- **`scene`** *(exists)* — per-handle mutable view state: currently displayed `AbstractId`, pan/scale/viewport-size transform, per-`ViewLayer` visibility, selection (`std::variant<TerminalId, ObstructionId>` — only the kinds with a rendered representation today). Distinct from the persistent database; the pipeline reads from it and events write into it. Built ahead of `pipeline` (moved up from the original build-order plan) since the shape-filter stage genuinely needs its scale for the sub-pixel threshold, not just as a future nicety — same lesson as `geometry` turning out to be a hard `io` dependency. Depends on: `database`, `view_style`.
- **`pipeline`** *(exists)* — a 4-stage pass (no node/task framework) over a `Scene`'s currently displayed Abstract, operating entirely in dbu-space: generate (tag with a cheap `ViewLayerPurpose`) → resolve `ViewLayerId` (a `Layer`-by-name + purpose lookup) → viewport/size-filter → layer-visibility-filter. Each stage is a non-static `Pipeline` instance method that caches its own last result, keyed on whatever it actually depends on (`generate`/`resolve` on `AbstractId` alone; the two filters additionally on `Scene`'s `viewport_version()`/`visibility_version()`), chaining to the previous stage internally — one `Pipeline` instance lives per `Scene`-equivalent lifetime and is reused across repeated calls. Resolving right after generating (on the full generated set) rather than after the viewport filter (on the ~25% that survive culling) costs more per Abstract switch (~+42ms at 1M shapes) but saves ~1.7ms on every subsequent pan/zoom frame — accepted since a one-time Abstract switch can show a loading spinner and affords up to ~1-2s, while pan/zoom is the actual latency-sensitive path. Current clean Release numbers: fresh-instance `run()` (cold) 96.7ms; reused-instance pan-only 6.30ms, visibility-only 0.625ms, no-change ~0ms. See `CLAUDE.md` for the design and `BENCHMARKS.md` for the full measurement/investigation, including an earlier separate-class design (`PipelineCache`) that was merged into `Pipeline` itself for readability. Depends on: `database`, `geometry`, `scene`, `view_style`.
- **`render`** *(new)* — applies the dbu → pixel transform (scale + pan + viewport offset, from `scene`) to the filtered shapes as its first step, then turns them into Skia draw commands and a pixel buffer for the Flutter texture. Depends on: `pipeline`, `scene`, `database`.
- **`events`** *(new)* — event definitions + dispatch for both C-API-originated events (load file, toolbar click) and surface-originated events (mouse move, object selection, resize/move), routing into `scene`/`database` mutations. Depends on: `scene`, `database`.
- **`properties`** *(new)* — generic get/set property access over a selected database object, keyed by object id + property name, for the Flutter property editor. Depends on: `database`.
- **`api`** *(new)* — the C API surface the Flutter plugin binds to: opaque-handle lifecycle (`init`/`destroy`), viewport control, file loading, the pixel-buffer render entry point, and buffer-based export of structural data (e.g. library/hierarchy browser). Depends on: everything above.

### Open design questions (resolve during implementation)

- **`properties`**: schema-driven reflection metadata (extend `cmg`/`schema.py` to emit per-field accessors) vs. hand-written per-class accessors.
- **Threading**: whether the pipeline stages need a task graph (e.g. Taskflow) at all, vs. plain threads/execution policies — decide only after a benchmark shows a bottleneck.
- **Skia integration**: raster-only linking strategy, and whether `SkPicture` recording is worth it vs. drawing straight to a canvas backed by the output buffer.
- **`api` pixel-buffer signature**: should be a platform-neutral raw-buffer signature for Linux, not a platform-specific pixel buffer type.
